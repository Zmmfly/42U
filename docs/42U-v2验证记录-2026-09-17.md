# 42U ABI v2 验证记录（2026-09-17）

## 本轮范围

基线为 `42fb5a9`（ABI v1 首版）。本轮改为 **invoke-only + 可撤销的协议租约**，ABI 主版本、命名空间与官方服务 IID 同步升级到 v2；项目版本为 `0.2.0`。本记录描述本轮工作树，不把旧 v1 验证记录当作新实现验收。本轮没有提交或推送。

- 消费者不获得提供者的业务接口指针，也不获得提供者 `iinvoke*`。
- 必须先以明确的 `contract{id, major, minor}` 借用实例，再凭 credential 绑定方法；调用统一经过宿主进入 `iinvoke`。
- `unbind` 只删方法绑定；`release` 才归还租约并使相关绑定失效。
- 未归还租约、在途调用和停止失败继续阻止不安全销毁；没有强制删除租约的兜底捷径。
- 协议族和 major 精确匹配、offered minor 不低于 required minor；协议兼容由提供者声明，不自动检查 JSON/schema 或任意业务语义。
- 重载后旧 credential/binding 不会跟随新实例。同协议也必须重新借用，消费者负责清除并重建会话、缓存及其他业务状态。

## 验证环境

Linux x86_64；C++17；64 位自然对齐；Itanium C++ ABI；GCC 15.2.0 / Clang 21.1.8；本机 libstdc++ / glibc 2.43；Xmake 3.0.8+dev.fe5d480。

ASan 显式使用 `ASAN_OPTIONS=detect_leaks=1:halt_on_error=1`；UBSan 显式使用 `UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1`。停止失败隔离用例在子进程中确认资源未销毁，再通过 `_Exit` 退出；它们不冒充正常退出泄漏检查。

### 协议与状态专项场景

`contract_test` 使用真实宿主和静态工厂插件，覆盖：

1. 协议族/major 不匹配、minor 不足拒绝，错误输出清零，失败借用不留下卸载锁。
2. 相同或足够高的兼容 minor 可借用并真实调用。
3. 同协议卸载重载，撤销回调清除消费者会话；新租约下旧会话在重新 open 前不存在。假提供者故意使用实例局部会话编号，重建后可复用相同编号，但旧 credential/binding 仍为 stale，证明隔离不依赖业务编号全局唯一。
4. 同 plug_id 升级到不兼容 major，旧消费者要求被拒，明确接受新契约后才能调用。
5. 多租约独立锁定；解绑不归还租约；归还一个不能解除另一个的锁。
6. 零凭据、跨 owner 凭据、错误线程受到检查，合法租约不受非法请求影响。
7. 提供者 invoke 内和结果 writer 交付期间尝试归还当前租约均返回 busy；调用返回后才可归还。
8. 提供者只在 commit 时被宿主查询 invoke_iid，acquire 不查询提供者，不产生业务指针。
9. 调用栈内卸载排队、未知 ID 不排队，结构 API 重入拒绝。
10. 管理端 revoker 也受回调深度保护，不绕过生命周期限制。
11. 一次性管理调用失败清理临时租约，不留下悬垂撤销接收端。

会话测试验证的是框架的代次隔离与消费者的显式重建流程，不代表框架会解析任意业务 session_id、自动迁移状态或阻止消费者在新租约下自行误用旧 JSON 数据。

## 独立审查与负向对照

- 无业务指针、lease owner/generation 校验、归还关联 binding 失效、在途计数、单次回调归还多个租约、借用环和停止失败锁保留经独立探针复核；未发现可复现的阻塞缺陷。
- 另一独立审查覆盖 native 一次性调用临时 receiver 寿命、分配失败恢复、错误输出、错线程拒绝及 ABI 协商；在合作式插件范围内未发现阻塞缺陷。中心将一次性调用的逐分配点失败检查补入持久 `boot_test`，不只依赖本地探针。
- ABI/SDK 检查以变异头为负对照：恢复 ABI 1、业务指针成员、旧 IID 或旧布局都会被断言拒绝。
- 协议测试短路 compatible_contract 或移除 active_calls 归还保护时会失败；consumer 的旧 start 内 bind 方式被加强后的状态模拟探针检出。
- 中心采纳测试审查建议，移除进程级唯一 session 计数对重载测试的遮蔽，改为允许业务编号在新实例中重复，分别验证会话重建和旧租约失效。
- 输出接收器可在交付期间发起另一次同步调用，当前不设置全局调用嵌套上限；这不是可信同进程模型下的强制资源隔离保证。消费者必须避免无界递归和死循环。

## 复现入口

顺序执行，不能并行切换同一项目的 Xmake 配置：

```bash
xmake f -m debug --toolchain=gcc --sanitizer=none -o build/v2 -y
xmake -j 8 && xmake test -v

xmake f -m debug --toolchain=gcc --sanitizer=address -o build/v2-asan -y
xmake -j 8 && ASAN_OPTIONS=detect_leaks=1:halt_on_error=1 xmake test -v

xmake f -m debug --toolchain=gcc --sanitizer=undefined -o build/v2-ubsan -y
xmake -j 8 && UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1 xmake test -v

xmake f -m release --toolchain=clang --sanitizer=none -o build/v2-clang -y
xmake -j 8 && xmake test -v

# 收尾已恢复此配置，并重新构建、运行 11/11 测试
xmake f -m debug --toolchain=gcc --sanitizer=none -o build -y
xmake -j 8 && xmake test -v
```

## 限制

- ABI v1 与 v2 不兼容。需迁移源码并重编，不能仅替换动态库继续使用旧宿主/SDK。拒绝旧版本以插件入口正确检查 major 为前提；谎报 ABI 或返回错误工厂类型违反可信插件契约，宿主不保证可安全识别。
- 仍是可信同进程、单控制线程模型，不提供内存隔离、崩溃隔离或进程内强制终止。
- 协议兼容性取决于提供者正确声明语义。框架不验证 JSON/schema，也不自动重放请求或恢复会话。
- 能力 watch 是发现通知，不能代替租约锁；极端 OOM 下排队通知视图构造仍可能失败。已建立依赖的卸载安全以同步租约撤销及是否实际归还为准，未归还时不得销毁。
- OOM 只保证定义的状态码边界与尽力清理；延迟卸载返回 failed 后需显式重试，不假设请求必定仍在队列。
- Windows、macOS、32 位及其他架构未验证；本轮没有运行新的 TSan 验证。跨编译器结果仅适用于本机上述固定 profile。
- 旧 [ABI v1 验证记录](42U首版验证记录-2026-09-17.md) 保留为历史证据，不覆盖本轮工作树。
