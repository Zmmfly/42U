# 42U 插件框架设计

> 文档版本：0.1（设计基线，尚未冻结二进制 ABI）
>
> 范围：可信的同进程 C++ 动态库插件；定义第一阶段的运行流程与接口契约。

## 1. 目标与设计原则

42U 是一个由宿主统一编排的插件机架：**宿主加载插件、安排初始化与启动、转发事件和能力披露、管理接口借用；插件通过事件发现彼此，再通过虚接口或动态方法调用协作。**

第一阶段的核心是制定支撑上述流程的插件 ABI，而不是只提供一个动态库加载器，也不是提前实现完整的应用运行时。

基本原则：

1. 启动时扫描并加载配置目录内的全部候选插件，不采用按能力需求懒加载。
2. 动态库与插件实例分别由 RAII 对象管理，释放顺序受生命周期约束。
3. 先完成全部插件初始化，再按相同顺序启动插件。
4. 初始化阶段建立事件监听，启动阶段通过宿主登记并广播能力。
5. 插件之间的接口获取必须经过宿主，宿主记录当前借用关系。
6. 撤销接口必须先通知、确认并排空调用，再销毁对象和卸载动态库。
7. 字符串方法名和数字方法 ID 使用同一套动态分发；类型化虚接口保留直接调用路径。

本文中的“必须”“不得”属于接口契约；“建议”属于实现建议。探索目录 `docs/thinks/` 中的方案不作为实现规范；与本文冲突时，以本文为准。

## 2. 第一阶段范围

| 纳入第一阶段 | 暂不纳入第一阶段 |
| --- | --- |
| 动态库扫描、ABI 校验和 RAII 管理 | 子进程 RPC、MCP 和跨机器传输 |
| 优先级与 before/after 初始化排序 | 运行中重排已经完成的初始化 |
| 初始化、启动、停止、销毁 | 暂停恢复、双实例无缝切换、状态迁移 |
| 基础事件订阅与能力披露 | waterfall、内容改写、脱敏策略引擎 |
| 类型化接口借用、撤销通知与动态卸载 | 不可信代码沙箱、强制终止进程内插件 |
| 按字符串或数字 ID 同步调用方法 | 跨边界异步调用、跨线程接口调用 |
| 单插件卸载后重新加载 | 插件业务状态自动恢复 |

借鉴 DSH 的能力与提供者分离、事件驱动组合、资源随作用域撤销等思想，但不照搬其运行时，也不以这些思想替代 C++ 对象寿命与二进制兼容性约束。

## 3. 核心对象与身份

### 3.1 职责划分

| 对象 | 职责 | 所有权 |
| --- | --- | --- |
| `plug` | 库映射、公共入口和卸载管理；宿主内部的动态库 RAII 包装，不属于 ABI | 宿主持有 |
| `iplug_fty` | 提供插件描述并创建实例 | 库内持有，宿主借用 |
| `iplug` | 插件实例的初始化、启动、停止、销毁与接口查询 | 宿主唯一拥有，销毁回到插件侧 |
| `ictx` | 注入插件的运行上下文，提供宿主通用虚接口入口 | 宿主持有，插件借用 |
| 能力记录 | 描述某个运行实例当前提供的接口或动态方法 | 宿主管理 |
| 接口借用记录 | 记录消费者、提供者和借用接口的关系 | 宿主管理，消费者持有借用凭据 |

宿主侧动态库包装命名为 `u42::plug`；基础 ABI 接口命名为 `u42::abi::v1::iplug_fty`、`u42::abi::v1::iplug` 和 `u42::abi::v1::ictx`，接口使用小写 `i` 前缀，`fty` 表示工厂，`ctx` 表示上下文。`v1` 表示基础 ABI 代际，不表示插件发布版本。`plug` 管理动态库资源，`iplug` 代表插件实例，二者的释放职责不得混同。

第一阶段每个动态库描述一种插件类型，每个插件 ID 同时只允许一个运行实例；不支持同 ID 的双实例热切换。

### 3.2 最小标识约定

插件侧只需理解三种公开标识，统一使用小写命名：

| 标识 | 含义 |
| --- | --- |
| `plug_id` | 插件稳定身份，使用非空 UTF-8 字符串，例如 `com.example.storage`；用于初始化排序、发现和调用 |
| `iid` | 一份冻结虚接口契约的 128 位标识；用于取得类型明确的虚接口，不随提供者变化 |
| `method_id` | 插件内唯一的方法数字 ID；与字符串方法名对应，不要求全局唯一 |

不再单独定义能力 ID：插件披露自己支持的 `iid` 和动态方法；接口按 `plug_id + iid` 获取，动态方法按 `plug_id + 方法名` 绑定。第一阶段同一插件对一个 `iid` 只提供一个实现，方法名和 `method_id` 分别在插件内唯一；同类多对象扩展留待实际需要时设计。

实例代次和借用记录编号由宿主内部维护，封装在不透明的借用凭据与方法绑定中，插件不自行构造、拆解或传递这些内部编号。凭据不能仅用可复用的对象地址表示；重载后旧借用失效、旧绑定调用报错，旧归还操作也不得匹配到新记录。通过 `plug_id` 重新查询则明确表示获取当前实例。

插件版本仍作为普通描述字段保留，不参与运行期寻址，也不用于推断 ABI 布局兼容性。

## 4. 宿主启动流程

```text
扫描配置的插件目录
    ↓
加载全部候选库，立即包装库句柄
    ↓
解析入口、校验 ABI、取得描述、创建并包装插件实例
    ↓
检查插件 ID 与初始化约束，计算唯一初始化计划
    ↓
按计划依次 init，注入宿主通用虚接口
    ↓
确认本批次全部插件初始化成功
    ↓
按同一计划依次 start
    ↓
每个 start 成功后提交能力登记，广播能力可用事件
    ↓
进入正常运行
```

### 4.1 扫描和加载

- 扫描范围由宿主配置限定，只处理约定命名规则或清单内的插件动态库；不遍历系统中的任意共享库。
- 同一规范化路径不得重复加载；不同库声明相同 `plug_id` 时拒绝本批次启动，不以扫描顺序决定覆盖关系。
- 每个加载成功的库必须立即进入 RAII 管理，再进行入口解析和实例创建。
- 插件必须把业务初始化、订阅和线程启动放进显式生命周期方法，不得放进全局构造函数或工厂描述查询中。加载库本身可能执行代码，因此扫描加载仅适用于可信插件。
- 第一阶段采用严格启动策略：缺少入口、ABI 不匹配、描述无效或任一插件创建失败时，本批次不得进入初始化；宿主报告失败并清理已创建对象。可选插件和降级启动策略不在本版隐式引入。

### 4.2 RAII 不等于任意时刻都能释放

宿主内部包装层负责最终资源归还，但运行实例的关闭必须通过显式卸载协议。不得让智能指针离开作用域后，直接销毁一个仍被调用或借用的插件。

释放先后关系为：

```text
收回外部借用、完成在途调用
    → 停止实例并撤销宿主注册
    → 在插件侧销毁实例
    → 释放宿主上下文
    → 解除库映射
```

库包装必须覆盖工厂、实例、能力接口、插件回调函数及所有仍指向插件代码的数据释放动作的寿命。

## 5. 初始化编排

### 5.1 声明与语义

插件描述必须在 `init()` 前可读，并包含初始化声明。以下仅为数据示意，不要求 ABI 使用 JSON，也不要求宿主引入 JSON 配置解析器：

```json
{
  "plug_id": "com.example.indexer",
  "init": {
    "priority": 100,
    "before": ["com.example.search"],
    "after": ["com.example.storage"]
  }
}
```

插件可以仅声明优先级，也可以使用 before/after，并为其指定优先级：

- `priority` 为有符号 32 位整数，默认 0，数值越小越先初始化。
- `A before B` 建立边 `A → B`；`A after B` 建立边 `B → A`。
- before/after 是硬约束，优先级只用于选择当前没有未满足前置约束的插件。
- 同优先级按 `plug_id` 的 UTF-8 字节序排序，结果不得取决于目录枚举顺序。
- 重复边去重；自引用、未知目标、约束成环均为启动错误，宿主必须报告相关插件。

宿主用拓扑排序生成计划。这里的 hook 指**初始化顺序约束**，不是允许插件调用另一个插件的 `init()`，也不是额外执行多次初始化。每个实例最多执行一次 `init()`。

### 5.2 初始化职责

`init()` 接收宿主上下文，并完成：

- 获取授予该实例的宿主通用接口；
- 建立事件订阅、能力监听和失效通知接收端；
- 准备实例内部资源。

初始化不得提前广播可用能力，也不得调用尚未启动插件的业务方法。初始化顺序不等于运行期依赖声明；例如 `after storage` 只保证 storage 先完成初始化，不表示 indexer 启动时 storage 的所有未来能力都会存在。

宿主记录初始化阶段创建的订阅和其他注册。`init()` 失败时插件回滚自身资源，宿主撤销此次初始化的注册；失败实例必须静默并可直接销毁。

## 6. 宿主通用接口与事件

`ictx` 通过版本化接口查询向插件提供能力，不暴露宿主实现类；注入插件时参数统一命名为 `ctx`。第一阶段至少需要以下职责；表中名称是 SDK 接口划分建议，不是已冻结的函数签名。

| 接口职责 | 最小操作 |
| --- | --- |
| 事件接口 | 订阅、取消订阅、发布事件 |
| 能力接口 | 登记能力、枚举现有能力、获取接口借用、归还借用 |
| 方法调用接口 | 按名称绑定方法、按绑定或名称发起调用 |
| 诊断接口 | 报告加载、初始化、调用和停止错误 |

宿主接口指针在 `init()` 调用开始至 `destroy()` 返回期间保持有效；操作是否允许仍受实例状态约束。销毁期间仅允许必要的资源归还和诊断，不得创建新订阅或发起业务调用。

基础事件规则：

1. 事件通过宿主排队投递，不在 `publish()` 调用栈内递归执行订阅者。
2. 插件回调在宿主控制线程串行执行，不得重入同一实例。
3. 订阅通过宿主登记并返回取消凭据；注册归属于订阅实例，卸载时由宿主统一撤销。
4. 插件可在初始化及运行期间订阅，不要求通过静态 manifest 声明全部订阅。
5. 普通发布输入为调用期间的只读视图，宿主成功受理前复制数据；回调数据默认只在回调期间有效。
6. 普通事件队列必须有容量上限，满时发布返回明确错误，不允许无限增长。
7. 生命周期通知不得因普通事件队列已满而静默丢弃；宿主使用独立的受控通知路径，并在安全调度点交付。无法完成通知时不得继续执行销毁。
8. `u42.*` 事件名由宿主保留，插件不得伪造能力上线、撤销等生命周期通知。

初始化期间只建立订阅，不投递插件回调；本批次全部初始化完成后才启用其回调。运行期新增插件也须在自身初始化成功后才接收回调。

## 7. 启动、能力披露与发现

### 7.1 能力登记与广播

所有插件初始化成功后，宿主按初始化顺序调用 `start()`。插件在 `start()` 中通过宿主登记其能力；登记先进入该实例的待提交集合。

每个插件的能力披露至少包含：

- 提供者 `plug_id`；
- 支持的 `iid` 列表及接口说明；
- 如支持动态调用，对应方法名称、`method_id` 和参数/结果格式说明。

不再要求插件为能力额外分配 ID。空能力集合合法，例如只消费事件的插件。

**只有 `start()` 成功，能力才成为可用状态。** 宿主先提交能力表，再发布 `u42.capability.available` 通知。失败时撤销待提交登记，不允许其他插件取得半启动实例的接口。

通知在插件的 `start()` 返回后的安全调度点投递，再继续启动后续插件。消费者可能尚处于 Initialized 状态，因此必须允许它接收能力通知、记录能力或申请接口，但不能提前执行业务调用。

宿主 `host::start()` 的成功表示本批全部实例在返回时仍为 Active，而不只是曾经完成启动。为此，创建、初始化、启动或能力通知回调中的已知实例卸载请求返回 `deferred` 并真正入队，但整个启动批次（包括失败回滚）不消费延迟卸载队列；能力通知的批次内投递不受影响。调用方在启动操作返回后使用 `poll()` 提供安全派发点，或显式 `unload()` 满足请求；其他批次外的安全清理也可能消费队列。`boot()` 和 `load()` 内部启动采用同一边界。请求不会跳过同批尚未执行的 `start()`，也不使成功返回时机架悄然缺少本批实例。

生命周期步骤失败时按既有协议回滚；内部分配失败（包括规划前的快照分配或回滚本身分配失败）只能尽力清理，可能留下 Created 或隔离记录供重试、关停，不提供所有失败都完成回滚的强异常保证。已销毁实例的延迟请求一并删除，不能作用于以后同 ID 的新实例。针对原有实例的请求仍保持排队，不由失败批次顺带执行。`deferred` 不表示卸载已经成功，后续执行仍可能因借用或停止失败而受阻；正常状态失败且存储允许时，请求重新入队供后续 `poll()` 重试。内部分配异常下队列仅尽力保留，收到 `failed` 后应显式重试 `unload(plug_id)`，不能假设请求一定仍在队列中。单次派发预算耗尽时，未处理事件、通知和延迟卸载均留到后续派发点。

### 7.2 能力表与监听配合

广播负责告知变化，能力表负责查询当前事实，二者缺一不可。

- 第一批插件在全部初始化完成后才开始接收披露，不会因尚未订阅而漏掉启动广播。
- 动态加载的消费者可以通过能力接口建立“监听并回送现有能力”的订阅；宿主在控制线程将登记监听和取得快照作为一个操作处理，后续变化按顺序接续。
- 消费者按 `plug_id` 查看披露，按 `iid` 选择接口；宿主在内部区分实例代次，保证旧实例撤回先于新实例上线，并丢弃不再有效的旧上线通知。重复观察不得创建无法归还的重复借用。
- 基础版本只允许在 `start()` 中登记能力，能力集合在该实例运行期固定；动态增删单项能力另行设计。

能力可用不等于所有消费者都已就绪。插件不得在自己的 `start()` 中同步等待排在后面的插件启动；需要的能力尚未出现时，应保持等待或不可服务状态，在通知到达后开展业务。

## 8. 虚接口获取与借用管理

### 8.1 获取流程

```text
消费者发现能力
    ↓
向宿主提交 plug_id、iid
    ↓
宿主校验当前提供者为 Active，且支持请求的精确接口
    ↓
宿主向提供者查询接口，并建立借用记录
    ↓
向消费者返回虚接口指针与不透明借用凭据
```

提供者查询接口不得启动业务工作或隐式转移所有权。宿主失败时不返回半有效借用；成功返回的接口地址在本次借用存续期间必须稳定。

宿主内部借用记录至少包含消费者实例、提供者实例代次、`iid` 和状态；消费者只持有用于归还的不透明凭据，不管理额外的借用 ID。记录的是**当前未归还借用**，不是历史上是否引用过。

### 8.2 使用约束

- 消费者不得直接销毁提供者接口，也不得跨边界 `delete` 插件对象。
- 消费者主动不再使用接口时，向宿主提交借用凭据完成归还，随后不得继续使用指针；SDK 的 RAII 包装可代为归还。
- 接口指针不得绕过宿主转交其他插件；另一个消费者必须独立申请借用。
- SDK 应提供只在消费者侧编译的 RAII 借用包装，封装指针与借用凭据，避免忘记归还；包装对象本身不进入 ABI。
- 提供者拥有接口实现；宿主拥有插件实例；消费者只有受撤销协议约束的借用权。
- 第一阶段业务调用和接口借用操作仅允许在宿主控制线程执行。消费者在 Initialized 状态可持有接口，但只有 Active 状态才能发起业务调用。

宿主无法通过裸指针自动发现所有复制，也无法天然拦截每次虚调用。上述规则是可信插件必须遵守的契约，不是内存隔离保证。后续若支持跨线程调用，必须增加受控调用守卫或代理及在途计数，不能只沿用当前单线程假设。

## 9. 动态卸载与失效通知

### 9.1 卸载流程

卸载请求由宿主统一执行，在插件调用栈已经退出的安全调度点开始：

1. **撤下能力**：将提供者置为 Revoking，从可获取能力表移除，拒绝新的借用和动态方法调用。
2. **通知能力撤回**：向能力监听者发布撤回通知；观察能力但未借用的插件也能获知变化。
3. **逐项撤销借用**：按借用记录向消费者发送 `interface_revoking` 通知，包含对应的不透明借用凭据；实例代次由宿主内部校验。
4. **确认归还**：消费者停止使用指针、清除缓存，在通知回调中归还对应借用；回调返回后宿主检查记录是否已归还。
5. **验证静默条件**：确认所有入向借用已归还、没有在途方法调用、没有待执行的提供者业务回调。
6. **停止提供者**：调用 `stop()`，收尾内部任务；停止成功后撤销它的订阅与宿主注册，并归还它持有的出向接口借用。
7. **销毁实例**：调用插件侧 `destroy()`，随后释放宿主上下文和实例包装。
8. **卸载动态库**：确认工厂引用、回调及其他插件代码引用全部消失后，解除库映射。

第一阶段失效通知为同步处理协议，不允许消费者返回后继续异步清理再使用旧指针。通知表示“即将失效”，不是“对象已销毁”；但消费者从收到通知起就不得再发起新的提供者业务调用。

### 9.2 拒绝卸载与失败隔离

- 消费者未归还借用、停止失败或无法证明静默时，不得销毁实例或卸载库。
- 提供者保留在不可获取新能力的隔离状态，宿主报告阻塞原因；本版不自动恢复已撤回的能力，也不隐式强制停止所有消费者。
- 超时不等于清理成功。控制线程中的插件调用卡住时，宿主也可能无法继续处理通知；进程内 ABI 不提供强杀保证。
- 插件内部线程必须在 `stop()` 成功前结束；不得把“库仍映射”当成后台线程可以访问已销毁对象的理由。
- 宿主受控退出时也遵守静默约束；无法完成时只能保留资源直至进程结束，不能声称已安全卸载。

接口借用图允许出现环。失效通知的作用是终止借用，不是在环上无限递归卸载。无法在失去某个能力后继续运行的消费者，应自行停止相关业务并报告状态，不得继续持有和调用即将失效的指针。

## 10. 单插件重新加载

重新加载采用“旧实例完整卸载，再创建新实例”的流程，不提供无空窗替换：

```text
旧实例撤销能力 → 收回接口 → stop → destroy → 卸载库
    ↓
加载新库 → 宿主更新内部实例代次 → init → start
    ↓
提交能力并重新广播 → 消费者重新申请接口
```

- 新实例必须重新初始化和启动，旧指针与旧方法绑定永不复活。
- 若旧实例卸载失败，不得用同一 `plug_id` 装入替代实例。
- 若新实例失败，能力保持缺失，宿主报告错误；不承诺自动恢复旧实例或业务状态。
- 初始化约束只编排尚未初始化的任务；对已运行实例不补执行或重放 `init()`。
- 对单插件热加载，`after` 指向已成功初始化且仍有效的实例时可以满足；`before` 指向已完成初始化的实例时不可满足，必须拒绝本次加载。目标不存在仍按未知目标报错，不静默忽略。

因此，声明了启动期前置约束的插件不一定能单独热加载。需要整体重新编排时，由运维或上层管理策略显式发起，不在底层 ABI 中偷偷重启其他插件。

## 11. 字符串、数字 ID 与类型化调用

三种调用方式并存：

| 路径 | 用途 | 规则 |
| --- | --- | --- |
| 字符串方法名 | 开发、调试、配置驱动调用 | 使用 `plug_id + 方法名`，方法名在插件内唯一 |
| 数字方法绑定 | 已完成解析后的重复调用 | 使用宿主返回的绑定；内部关联实例代次和 `method_id` |
| 类型化虚接口 | 编译期已知接口的直接调用 | 使用 `plug_id + iid` 取得借用，遵守接口 ABI 与撤销规则 |

逻辑上的动态调用链为：

```text
plug_id + 方法名（或 method_id）
    → 查找当前可用实例
    → 按名称解析或校验 method_id，生成不透明方法绑定
    → 通过绑定进入同一个同步调用入口
```

插件不维护两套方法实现。方法名和 `method_id` 分别在插件内唯一；需要分组时可使用 `file.read` 等带前缀的方法名，不引入独立能力 ID。未知名称、未知 ID、提供者撤回或绑定代次过期均返回明确错误。

便捷调用可每次按 `plug_id + 方法名` 或 `plug_id + method_id` 解析当前实例；重复调用则复用宿主返回的方法绑定。重载后方法数字可以再次出现，但旧绑定不得自动指向新实例；调用方必须重新发现方法并绑定。

第一阶段动态调用采用 UTF-8 JSON 字节序列作为参数和结果格式，具体 schema 随方法披露；类型化虚接口不要求 JSON 序列化。

为避免返回数据的释放函数继续引用待卸载库，第一阶段同步动态调用采用：

- 输入为仅本次调用有效的只读字节视图；
- 输出写入调用方提供的 ABI 写入接口，数据由调用方持有，接收端按配置限制大小；
- 插件不得保存输出接口或在返回后继续写入；
- 调用失败时丢弃部分输出并返回状态码。

数字方法绑定不自动延长实例寿命，宿主每次调用前校验代次和状态；虚接口借用则必须显式归还。两种路径的有效性管理不能混为一谈。

## 12. 生命周期、线程和失败清理

### 12.1 状态与操作

| 状态 | 允许的主要操作 | 退出方式 |
| --- | --- | --- |
| Created | 读取描述、调用一次 `init()` | 初始化成功，或直接销毁 |
| Initialized | 监听能力、保存接口借用、调用一次 `start()` | 启动成功，或 `stop()` 清理 |
| Active | 处理事件、调用业务能力、获取和归还借用 | 进入 Revoking |
| Revoking | 处理撤销与归还，不接受新业务 | 满足条件后 `stop()` |
| Stopped | 不再工作，无插件线程或业务回调 | `destroy()` |
| Faulted | 诊断与隔离，不恢复业务入口 | 保留资源或受控退出 |
| Destroyed | 无操作；一切实例指针失效 | 无 |

`init()` 失败必须回滚至可直接销毁的静默状态。`start()` 失败必须撤销启动工作并回到 Initialized，宿主随后调用 `stop()` 清理初始化资源。`stop()` 同时适用于已初始化但未启动的实例和正常停止的实例，成功后不允许再次启动。

插件 `stop()` 负责释放自身资源、结束内部线程和停止主动回调；宿主负责关闭分发入口、撤销登记、管理借用并防止新的回调进入。二者共同完成停止，不能把全部责任交给任意一方。

### 12.2 启动批次失败与正常退出

第一阶段不提供部分成功的隐式启动：

- 初始化失败时，不启动任何插件；对已初始化实例按计划逆序执行 `stop()`，对未初始化及已回滚失败的实例直接销毁。
- 启动失败时，中止后续启动；先撤回已启动实例的能力，按借用协议清理关系，再按计划逆序停止已初始化实例。
- 正常全局退出时，先关闭全局业务入口，再撤回能力和处理全部借用，最后按初始化计划逆序停止和销毁。
- 清理顺序只是默认编排；是否可以销毁仍取决于借用、调用和停止结果，不能仅凭“逆序”推断安全。

### 12.3 线程模型

第一阶段采用单一宿主控制线程：生命周期、能力查询、事件回调、动态调用及跨插件虚接口调用均在该线程上执行。不同插件间的同步调用允许嵌套，但不得形成对同一实例的重入；SDK 和插件必须遵守这一约束。

卸载请求在调用栈非空时只对已知实例排队，不立即执行；未知 ID 返回 `not_found`，不为未来实例留请求。启动批次中的队列消费边界见第 7.1 节。回调中的 `add()`、`boot()`、`load()`、`shutdown()` 返回 `busy`，`start()` 返回 `invalid_state`，不隐式安排重试。插件不得在回调中同步等待由同一控制线程处理的后续事件；`stop()` 也不得等待该线程替自己完成排队任务。

调用方必须保证 `host` 在任何宿主操作及插件回调执行期间存活，不得在回调中销毁宿主；`shutdown()` 的重入保护不能使 `delete host` 成为合法的对象寿命操作。返回 `status` 的 native 操作在内部把异常转换为状态码，诊断分配失败时允许保留旧诊断，以返回状态为准。构造函数与 `plugins()` 的快照分配仍可能抛异常；调用方准备字符串、路径等实参时的分配也不在该转换边界内。

插件内部可以使用工作线程处理私有计算，但不得从工作线程调用宿主或其他插件接口，也不得把接口借用指针交给工作线程。后续引入跨线程投递时，必须另行定义所有权、取消和排空协议。

## 13. ABI 与 SDK 交付约束

### 13.1 二进制边界

采用 **C 链接入口 + 受约束的 C++ 纯虚接口**：

- 动态库通过一个明确导出的入口协商基础 ABI 主版本并返回工厂；不支持时返回错误，不返回可调用对象。
- 工厂提供初始化前可读的描述并创建实例；根实例接口承载 `init/start/stop/destroy` 与能力接口查询。
- 接口只有纯虚函数，无数据成员；能力指针由接口查询返回，不得从根对象地址推算其他接口地址。
- 跨界类型限定为固定宽度整数、已定义布局的简单结构、不透明标识、指针与长度视图、纯虚接口指针。
- STL、异常、RTTI 对象、线程对象和协程句柄不跨边界；边界函数使用 `noexcept`，异常在产生侧转换为状态码。
- 对象由分配方销毁；宿主调用插件的 `destroy()`，消费者不销毁借用接口。
- 发布后的接口槽位、签名和语义不可修改，也不可在旧 `iid` 下追加槽位；新增契约分配新 `iid`。

`extern "C"` 不保证 C++ 虚接口跨平台兼容。SDK 必须规定并测试支持的操作系统、架构、位宽、调用约定、C++ ABI 家族、结构体对齐和运行时基线。

### 13.2 宿主公共契约必须成套交付

第一阶段 SDK 必须同时给出以下声明和语义，不得仅交付一个根接口头文件：

1. 入口、工厂、插件描述及初始化排序结构。
2. 插件生命周期和宿主上下文接口。
3. 事件订阅、取消与回调接口。
4. 能力描述、登记、快照监听和查询接口。
5. 接口借用结果、归还操作及撤销通知接口。
6. 方法描述、名称绑定、数字调用和结果写入接口。
7. 状态码、官方接口 ID、平台导出与调用约定宏、结构体布局断言。
8. 宿主与插件两侧的 RAII 辅助包装；包装为源级工具，不进入 ABI。

错误输出必须有统一规则：必需指针为空返回参数错误；合法输出地址先清空再执行；失败不遗留半有效实例、接口借用或方法绑定。描述字符串与数组的有效期、字符串编码、空值规则和尺寸检查方式必须在对应头文件逐项说明。

本文确定运行模型和契约；上述接口的精确签名、常量值及支持平台矩阵仍需在 SDK 实现评审中冻结，不能把设计文档存在视为 ABI 已通过验证。

## 14. 第一阶段验收标准

通过 xmake 构建独立宿主和示例动态库，至少覆盖以下验证：

| 类别 | 验证内容 |
| --- | --- |
| 扫描与加载 | 全部候选插件被发现；重复 ID、入口缺失、ABI 不匹配明确失败；中途失败资源可清理 |
| 初始化排序 | 纯优先级、before/after 混用、同优先级稳定排序、未知目标及环检测；每实例只 init 一次 |
| 两阶段启动 | 首次 start 前全部 init 完成；启动顺序与初始化计划一致 |
| 能力披露 | start 成功前不可取得能力；失败不泄漏登记；晚加入消费者取得快照及后续变化 |
| 接口借用 | 多消费者、多借用、主动归还、消费者先卸载；借用记录与内部实例代次正确，旧归还凭据不会影响新借用 |
| 动态卸载 | 先撤销后销毁；未归还或停止失败时不卸载；待执行回调不会进入已销毁实例 |
| 重新加载 | 新代次重新披露；旧借用及方法绑定失效；不可满足的热加载排序约束明确拒绝 |
| 方法调用 | 字符串和数字绑定结果一致；插件内方法名及 `method_id` 分别唯一；未知方法、过期绑定和输出大小限制返回明确错误 |
| 失败回滚 | init/start 失败与全局退出路径清理正确；原有借用环不会导致递归卸载 |
| ABI 兼容 | 保留旧插件二进制供新宿主加载；支持旧契约的新插件可由旧宿主使用；不是仅双方一起重编 |
| 资源与线程 | 多轮装卸不泄漏实例与注册；stop 成功后无后台线程和回调；使用可用的内存检查工具验证 |

最小示例应包含一个能力提供者和一个消费者：验证初始化时监听、启动时披露、字符串与虚接口调用、撤销确认，以及重载后的重新获取。

**第一阶段完成的标志，是上述流程能被真实插件验证，而不是接口数量足够少或术语足够完整。**
