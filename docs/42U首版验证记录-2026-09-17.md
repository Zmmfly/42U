# 42U 首版收尾验证记录（2026-09-17）

## 范围与结论边界

本轮接续本地交接文档，对已有首版实现收尾，不重建框架，不提交或推送。验证对象是工作树，而不是仅包含设计文档的 HEAD `340dc7114b4e231bc04777e153a48ce4b36e06e0`。多数实现文件仍未跟踪，不能用 HEAD 哈希代表已验收源码。

本轮明确的启动契约：每个插件启动后的能力通知仍在批次内交付，但延迟卸载队列在整个启动批次及失败回滚期间保持排队。`host::start()` 成功返回时本批插件仍全部 Active；随后由 `poll()`、显式卸载或批次外安全清理处理请求。正式约束见[设计第 7.1 节](42U插件框架设计.md#71-能力登记与广播)及 `inc/42u/host.hpp`。

同时补齐宿主寿命、线程、异常及输出参数的公共文档，并修复 native `bind` / `unbind` / `call` 在 `try` 外构造参数错误诊断可能再次抛分配异常的问题。独立审查发现 `poll()` 的第二套卸载循环会重复消费并丢失受阻请求，现统一由分发器管理队列：首次 `busy` 保留请求，消费者可归还后再次 `poll()` 完成卸载。预算耗尽时所有未处理工作留待后续派发。回滚文档明确分配失败仅提供尽力清理，不保证没有残留记录。

Clang 全量构建暴露 `safety_test` 中 `struct` 前置声明与 `class` 定义不一致，已统一为 `class`，没有关闭 warnings-as-errors。

## 环境

- Linux x86_64，内核 `7.0.0-31-generic`。
- GCC `15.2.0`，Clang `21.1.8`，本机 libstdc++ / glibc `2.43`。
- Xmake `3.0.8+dev.fe5d480`，C++17，64 位自然对齐，Itanium C++ ABI。
- ASan 验证显式设置 `ASAN_OPTIONS=detect_leaks=1:halt_on_error=1`。
- UBSan 验证显式设置 `UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1`。

## 可复现入口

各配置必须顺序执行，不能并行修改同一 `.xmake` 配置。

```bash
xmake f -m debug --toolchain=gcc --sanitizer=none -o build -y
xmake -j 8 && xmake test -v

xmake f -m debug --toolchain=gcc --sanitizer=address -o build/asan -y
xmake -j 8 && ASAN_OPTIONS=detect_leaks=1:halt_on_error=1 xmake test -v

xmake f -m debug --toolchain=gcc --sanitizer=undefined -o build/ubsan -y
xmake -j 8 && UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1 xmake test -v

xmake f -m release --toolchain=clang --sanitizer=none -o build/clang -y
xmake -j 8 && xmake test -v

# 恢复普通开发配置
xmake f -m debug --toolchain=gcc --sanitizer=none -o build -y
```

混合编译器验证复用完整 `integration_test`，不只检查动态库能否打开：

## 验收项对应

| 设计第 14 节类别 | 持久测试或验证入口 | 边界 |
| --- | --- | --- |
| 扫描与加载 | `integration_test`：目录负例、缺入口、ABI 拒绝、重复身份 | 真实平台 DSO；不扫描系统插件目录 |
| 初始化排序 | `order_test`、`runtime_test` | priority、硬边、稳定顺序、未知目标、环和热加载约束 |
| 两阶段启动 | `runtime_test`、`reentrant_test` | 首次 start 前全部 init；批次中自卸载与先/后启动的同批目标均不被提前清理 |
| 能力披露 | `runtime_test`、`event_test`、`integration_test` | Initialized 消费者允许借用但不允许业务调用；监听快照仍通过队列 |
| 接口借用 | `runtime_test`、`safety_test`、`sdk_test` | 多借用、归还、消费者先卸载、旧凭据与重载代次 |
| 动态卸载 | `integration_test`、`safety_test`、`reentrant_test`、`withdraw_test` | 真实 DSO 装卸；拒绝归还与停止失败隔离；撤回分配失败原子性 |
| 重新加载 | `integration_test`、`runtime_test`、`reentrant_test` | 旧绑定失效、重新借用、旧延迟请求不得影响新实例 |
| 方法调用 | `runtime_test`、`integration_test`、CLI 名称/数字调用 | 同一方法分发、非法参数、未知方法、输出限额及失败清空 |
| 失败回滚 | `boot_test`、`runtime_test`、`reentrant_test` | boot 旧身份快照分配失败、新动态批次失败、init/start 失败、借用环；批次失败不得顺带消费原有实例的卸载请求 |
| ABI 兼容 | `abi_test`、GCC/Clang 双向混合 `integration_test` | 只证明本轮固定 profile；无历史 SDK 二进制兼容认证 |
| 资源与线程 | `event_test`、`withdraw_test`、多轮真实装卸及 ASan/UBSan | 持久错线程回归只覆盖实际用例；不把历史临时 TSan 扫描当本轮结果 |

停止失败的消费者必须保留出向借用，可能连带保留提供者；这是安全契约，不以清空借用记录规避。`safety_test` 的隔离用例在子进程中确认没有销毁，再通过 `_Exit` 结束；其刻意触发 CHECK 的子进程用于证明 NDEBUG 下断言仍致命，日志中的该条 CHECK failure 是预期探针，不是整套测试失败。

## 未验证项与交付限制

- Windows、macOS、32 位、其他架构及跨历史 SDK 版本仍未验证。当前并无历史发布二进制，不宣称设计第 14 节的历史兼容认证已经完成。
- 本轮不重新执行交接提及的 `/tmp` 历史全量故障注入或 TSan 脚本；长期回归以仓库测试为准。
- 内部分配异常仅提供尽力清理和队列保留；`poll()` 返回 `failed` 后，调用方应显式重试 `unload(plug_id)`，不能假定延迟请求仍在队列中。正常 `busy` 状态重试已由持久回归验证，不把它扩大为 OOM 下的强持久性保证。
- 可信插件模型不拦截裸虚接口指针的非法复制或跨线程使用，不提供进程内强制终止；宿主回调中销毁 host 仍属契约违反。
- 原有暂存区保持不变。其 `.gitignore:4` 的 EOF 空行警告在接手前已存在，不在本轮修改范围。
- 本地构建日志位于忽略目录 `build/validation/`，不作为需要提交的产物。
